# PL-10: Add AI Chat but still just Mutual NDA

## Context

Jira PL-10 asks to replace the current "series of questions" flow with a free-form AI chat: the AI converses with the user, asks about the document's fields, and populates the Mutual NDA based on responses. Scope stays limited to the Mutual NDA — no new document types.

Today the app is fully client-side and stateless: `frontend/src/app/page.tsx` renders a manual field-by-field form (`NdaForm.tsx`) next to a live preview (`NdaDocument.tsx`), both driven by `NdaFormData` (8 fields) from `frontend/src/lib/ndaTemplate.ts`. There is no backend call anywhere in the frontend. The backend (`backend/app/main.py`) only exposes `GET /api/health` and static file serving; Postgres only has a `users` table with no signup/signin logic wired to it. Login (`frontend/src/app/login/page.tsx`) just sets a `localStorage` flag — no request is made. The project already has a documented pattern (`.claude/skills/cerebras/SKILL.md`) for calling an LLM (`gpt-oss-120b` via OpenRouter/LiteLLM, Cerebras as inference provider) with Pydantic Structured Outputs, and `OPENROUTER_API_KEY` is already in the root `.env`.

Decisions confirmed with the user:
- Chat/draft state is **persisted in Postgres** (not stateless in the frontend).
- The draft is **linked to a real `users` row** — the fake login form now calls a backend endpoint that creates-or-finds a user by email (still no password verification) and returns a user id, which the frontend stores and sends with every chat request.
- The manual `NdaForm` inputs are **removed entirely**, replaced by chat. `NdaDocument` preview stays and updates live.
- Completion (download-ready) is decided **by the frontend**, checking whether all 8 fields are non-empty — not an LLM-reported flag.

Outcome: a chat-driven NDA intake that persists conversation + field state per user, replacing the manual form while reusing all existing template/PDF/preview logic unchanged.

## Database schema (new Alembic migration, `down_revision = "0001"`)

**`nda_drafts`** — one active draft per user for V1 (enforced via a unique index on `user_id`; a later ticket can relax this for multi-draft support).
- `id` serial PK
- `user_id` integer NOT NULL, FK → `users.id`, unique
- `party_a_name`, `party_b_name`, `effective_date`, `purpose`, `mnda_term`, `term_of_confidentiality`, `governing_law`, `jurisdiction` — all `text`, nullable (mirrors `NdaFormData`'s 8 fields as discrete columns, not JSON — simpler with Core `Table`, directly queryable)
- `created_at`, `updated_at` timestamptz, `server_default now()` (bump `updated_at` in application code on each turn)

**`nda_draft_messages`**
- `id` serial PK
- `draft_id` integer NOT NULL, FK → `nda_drafts.id`
- `role` varchar(20) NOT NULL (`"user"` / `"assistant"`; system prompt is built fresh each call, not stored)
- `content` text NOT NULL
- `created_at` timestamptz server_default now()
- index on `draft_id`

Follow `backend/migrations/versions/0001_create_users_table.py`'s style exactly (plain `sa.Column`/`op.create_table`, no ORM).

## Backend changes

- `backend/pyproject.toml` — run `uv add litellm pydantic` in `backend/` (updates lock file too).
- `backend/app/models.py` (new) — SQLAlchemy Core `Table` defs for `users` (replicated for querying), `nda_drafts`, `nda_draft_messages` on a shared `MetaData()`; Pydantic schemas `NdaFormData` (8 `str` fields, default `""`), `LoginRequest`/`LoginResponse`, `ChatRequest`/`ChatResponse`, `DraftResponse`.
- `backend/app/llm.py` (new) — Pydantic `NdaChatTurn(BaseModel)` with the 8 field names + `reply: str` (structured-output schema); `build_system_prompt(current_fields) -> str` describing each field's purpose (drawn from the Standard Terms context in `ndaTemplate.ts`), instructing the model to converse naturally, never fabricate values, ask clarifying follow-ups, and always return **all 8 fields as a full snapshot** (carrying forward previously-known values supplied in the prompt, only changing what the latest message clearly supplies) rather than a patch — this matches the frontend simply overwriting its `NdaFormData` state each turn; `run_chat_turn(history, current_fields, user_message) -> NdaChatTurn` calling:
  ```python
  litellm.completion(
      model="openrouter/openai/gpt-oss-120b",
      messages=messages,
      reasoning_effort="low",
      extra_body={"provider": {"order": ["cerebras"]}},
      response_format=NdaChatTurn,
  )
  ```
  (Corrects the typos in `.claude/skills/cerebras/SKILL.md` — real API is `litellm.completion`, `reasoning_effort` singular.)
- `backend/app/routers/__init__.py`, `auth.py`, `nda.py` (new) — move endpoint logic out of `main.py` into routers, included via `app.include_router(...)`.
  - `POST /api/auth/login` — body `{"email": str}`; `SELECT`-or-`INSERT` into `users` by email, no password check; returns `{"user_id": int, "email": str}`.
  - `POST /api/nda/chat` — body `{"user_id": int, "message": str}`; loads-or-creates the user's `nda_drafts` row, loads ordered message history, calls `run_chat_turn`, persists the new user+assistant messages and updated field columns, returns `{"reply": str, "fields": {...8 keys...}}`.
  - `GET /api/nda/draft?user_id=` — returns `{"fields": {...}, "messages": [...]}` so a page refresh restores state; seed one opening assistant message at draft-creation time so both this and the first chat POST see a consistent starting point.
- `backend/app/main.py` — trim to app setup + router includes; keep `/api/health` and static serving as-is.
- `backend/app/db.py` — unchanged; routers use `engine.begin()` with Core `insert`/`select`/`update`.
- No new `config.py`/pydantic-settings — keep the existing raw `os.environ` + `python-dotenv` pattern (`llm.py` calls `load_dotenv()` itself, matching `db.py`'s self-contained style).

## Frontend changes

- `frontend/src/lib/fakeSession.ts` — replace the boolean flag with a stored user id (`getUserId()`, `setUserId(id)`, `clearSession()`).
- `frontend/src/lib/api.ts` (new) — small fetch wrapper: `login(email)`, `getDraft(userId)`, `sendChatMessage(userId, message)`. Same-origin calls (FastAPI serves the static export), no base-URL config needed.
- `frontend/src/app/login/page.tsx` — on submit, call `login(email)` (password field stays in the UI for continuity but is not sent), store the returned user id, handle loading/error state (first real network call in the app).
- `frontend/src/components/NdaChat.tsx` (new, replaces `NdaForm.tsx`) — scrollable message list (user/assistant bubbles) + input + send button, loading/error states while awaiting the backend. Reuse existing Tailwind utility classes (`blue-600`/`purple-700`/`gray-900`/`gray-50`) consistent with the rest of the app rather than introducing new brand-hex tokens now — out of scope for this ticket.
- `frontend/src/app/page.tsx` — on mount, after confirming a user id exists, call `getDraft` to hydrate `fields` + `messages`; replace `<NdaForm>` with `<NdaChat>`; `handleSend` posts to `/api/nda/chat`, appends the reply to `messages`, and sets `fields` from the response; gate the existing PDF/txt download buttons on `Object.values(fields).every(v => v.trim() !== "")`. `NdaDocument` stays unchanged, still rendering from `fields`.
- Delete `frontend/src/components/NdaForm.tsx` (no longer used).

## Docker/config

No changes needed: `docker-compose.yml`'s `app` service already has `env_file: [.env]`, which already contains `OPENROUTER_API_KEY`. The `uv.lock` update from `uv add litellm pydantic` will be picked up automatically by the existing `uv sync` in the Dockerfile once committed.

## Testing

Backend (`backend/tests/`), following existing patterns (`test_health.py`'s `TestClient` + `unittest.mock.patch`, `test_db.py`'s skip-if-Postgres-unreachable marker):
- `test_auth.py` — login is idempotent (same email → same `user_id`); creates a new row for a new email.
- `test_llm.py` — unit test `run_chat_turn`/`build_system_prompt` by mocking `litellm.completion` to return canned structured JSON; assert parsing and that current field values are injected into the prompt.
- `test_nda_chat.py` — integration test against real/skippable Postgres, patching `run_chat_turn` at its point of use (`app.routers.nda.run_chat_turn`), verifying: draft auto-creation on first message, ordered message persistence, field-column updates, response shape, and draft reuse on a second call.

Frontend: `frontend/package.json` has no test runner (only `eslint`) — do not introduce one for this ticket. Verify manually via `npm run dev` + local `uvicorn`/`docker compose up`: login → chat through all 8 fields → confirm live preview updates → confirm download buttons only enable once all fields are filled → refresh mid-conversation and confirm state restores via `GET /api/nda/draft`.

## Steps

1. Run `uv add litellm pydantic` in `backend/`.
2. Write Alembic migration `0002_create_nda_chat_tables.py` (creates `nda_drafts` and `nda_draft_messages`).
3. Add `backend/app/models.py` (Core table defs + Pydantic schemas) and `backend/app/llm.py` (`NdaChatTurn`, `build_system_prompt`, `run_chat_turn`).
4. Add `backend/app/routers/auth.py` (`POST /api/auth/login`) and `backend/app/routers/nda.py` (`POST /api/nda/chat`, `GET /api/nda/draft`); wire both into `backend/app/main.py`.
5. Write backend tests (`test_auth.py`, `test_llm.py`, `test_nda_chat.py`) and run `pytest`.
6. Update `frontend/src/lib/fakeSession.ts` (user-id-based session) and add `frontend/src/lib/api.ts` (fetch wrapper).
7. Wire `frontend/src/app/login/page.tsx` to the real `/api/auth/login` call with loading/error handling.
8. Build `frontend/src/components/NdaChat.tsx`; delete `frontend/src/components/NdaForm.tsx`.
9. Rewrite `frontend/src/app/page.tsx` to hydrate from `GET /api/nda/draft`, wire the chat, and gate downloads on field completeness.
10. Manually verify end-to-end via `docker compose up` or local dev servers (login → chat → live preview → gated downloads → refresh-resume).
11. Update root `CLAUDE.md`'s "Implementation Status" section to describe the chat-based flow, new tables, and new endpoints.
